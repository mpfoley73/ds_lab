How to use renv and venv for reproducible data science in R and Python, with examples and deployment tips.

Published

April 27, 2026

Overview

This tutorial provides a comprehensive introduction to virtual environments in data science, with a focus on R users who may also work with Python. We’ll explore the conceptual foundations, practical reasons for using virtual environments, common use cases in data science workflows, and the mechanics of implementation in both R and Python. The tutorial includes hands-on examples and deployment considerations to give you both functional knowledge and conceptual understanding suitable for presenting to peers.

Setup

Before we begin, let’s configure our Python environment for the examples in this tutorial.

Why Use Virtual Environments?

Virtual environments are isolated spaces where you can install and manage project-specific dependencies without affecting your system’s global package installations. This isolation prevents conflicts and ensures reproducibility.

Key Benefits

  1. Dependency Isolation: Each project maintains its own set of packages and versions, preventing “dependency hell” where different projects require conflicting package versions.

  2. Reproducibility: By locking exact package versions, you can recreate the exact same environment on different machines or at different times, ensuring analyses produce consistent results.

  3. Collaboration: Team members can easily recreate your environment, reducing “works on my machine” issues.

  4. System Stability: Your global R/Python installation remains clean and stable, unaffected by project-specific changes.

  5. Deployment Readiness: Lockfiles make it straightforward to deploy applications with known, tested dependencies.

The Problem Without Virtual Environments

Imagine you’re working on multiple data science projects:

  • Project A uses dplyr 1.0.0 and ggplot2 3.3.0
  • Project B requires dplyr 1.1.0 and ggplot2 3.4.0

Without virtual environments, upgrading packages for Project B might break Project A. Virtual environments solve this by giving each project its own package sandbox.

Common Use Cases in Data Science

Research and Academic Work

  • Reproducible Research: Journals increasingly require code and data to reproduce results. Virtual environments ensure the exact packages used are preserved.
  • Long-term Archival: Analyses from years ago can still run with the original environment.
  • Peer Review: Reviewers can recreate your exact setup to verify results.

Teaching and Education

  • Consistent Student Environments: All students get the same package versions, avoiding confusion from version differences.
  • Course Materials: Tutorials and assignments work reliably across different student machines.

Production and Deployment

  • Model Deployment: Machine learning models deployed to production need the exact same environment used during training.
  • Web Applications: Shiny apps or Streamlit apps require consistent dependencies across development, staging, and production.
  • API Services: Data science APIs must have predictable package versions to ensure stable behavior.

Multi-language Projects

  • R + Python Integration: Projects using both languages (via reticulate) need coordinated environments.
  • Legacy Code Migration: Gradually migrate from one language to another while maintaining separate environments.

Core Concepts

Before diving into mechanics, let’s understand the key concepts:

  • Environment: A project-specific collection of packages with their versions.
  • Lockfile: A file that records exact package versions and sources, enabling perfect recreation of the environment.
  • Snapshot: The process of recording current package versions to a lockfile.
  • Restore: Installing packages from a lockfile to recreate an environment.
  • Isolation: Keeping project dependencies separate from system-wide installations.

R: renv (The Standard Approach)

renv is the recommended tool for managing R package environments. It creates a project-local library and generates a renv.lock file that captures exact package versions and sources.

Basic Workflow

  1. Initialize: Set up renv for your project
  2. Install Packages: Add packages as needed during development
  3. Snapshot: Record current package state to renv.lock
  4. Restore: Recreate the environment from renv.lock on another machine

Core Commands

Initialize renv in your project directory:

# One-time setup per project
renv::init()

Install packages during development:

# Install packages as you work
install.packages("dplyr")
install.packages("ggplot2")

Snapshot your current environment:

# Record exact versions to renv.lock
renv::snapshot()

Restore environment on another machine:

# Install packages exactly as in renv.lock
renv::restore()

How renv Works

  • Creates a renv/ directory with project-specific package installations
  • Generates renv.lock with exact versions, sources, and dependencies
  • Modifies .Rprofile to automatically activate the local environment
  • Provides tools for managing package conflicts and updates

Best Practices for R Projects

  • Always commit renv.lock to version control
  • Never commit the renv/library/ directory (it’s large and machine-specific)
  • Run renv::snapshot() after installing new packages
  • Use renv::status() to check for discrepancies between lockfile and current environment

Python: venv and Poetry

Python offers several virtual environment tools. We’ll cover the built-in venv and the more advanced poetry.

venv: Built-in Virtual Environments

venv creates isolated Python environments using the standard library.

Basic Commands

Create a virtual environment:

# Create environment in .venv directory
python -m venv .venv

Activate the environment:

# On Windows
.venv\Scripts\activate

# On macOS/Linux
source .venv/bin/activate

Install packages:

pip install pandas numpy matplotlib

Create requirements file:

pip freeze > requirements.txt

Install from requirements:

pip install -r requirements.txt

Poetry: Advanced Dependency Management

Poetry provides deterministic dependency resolution and better lockfile management.

Basic Commands

Initialize a Poetry project:

poetry init

Add dependencies:

poetry add pandas numpy

Install dependencies:

poetry install

Activate the virtual environment:

poetry shell

Python Best Practices

  • Use .venv or venv as directory name (add to .gitignore)
  • Commit requirements.txt or poetry.lock + pyproject.toml
  • Specify Python version in your environment
  • Use pip-tools or Poetry for complex dependency trees

Using Python from R (reticulate)

The reticulate package allows seamless integration between R and Python.

Setting Up reticulate with Virtual Environments

Create and configure a Python environment:

# Install reticulate if needed

# Configure reticulate to use this environment

Using Python Objects in R

# Use Python objects
df <- pd$DataFrame(list(x = c(1, 2, 3), y = c(4, 5, 6)))
print(df)

Shiny App for Deployment

For demonstration purposes, we’ve included a simple Shiny app:

Show the code 
library(shiny)
library(ggplot2)

ui <- fluidPage(
  titlePanel("Virtual Environment Demo"),
  sidebarLayout(
    sidebarPanel(
      sliderInput("n", "Number of points:", 10, 1000, 100),
      selectInput("color", "Color:", c("blue", "red", "green"))
    ),
    mainPanel(plotOutput("plot"))
  )
)

server <- function(input, output) {
  output$plot <- renderPlot({
    set.seed(123)
    df <- data.frame(x = rnorm(input$n), y = rnorm(input$n))
    ggplot(df, aes(x, y)) +
      geom_point(color = input$color) +
      theme_minimal()
  })
}

shinyApp(ui, server)

GitHub Actions for CI/CD

GitHub Actions can automate environment setup and testing.

Basic CI Workflow

yaml

Show the code 
name: R + Python CI

on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        r-version: [4.3]
        python-version: [3.10]
    
    steps:
    - uses: actions/checkout@v4
    
    - name: Setup R
      uses: r-lib/actions/setup-r@v2
      with:
        r-version: ${{ matrix.r-version }}
    
    - name: Setup Python
      uses: actions/setup-python@v4
      with:
        python-version: ${{ matrix.python-version }}
    
    - name: Restore R environment
      run: |
        R -e 'install.packages("renv")'
        R -e 'renv::restore()'
    
    - name: Setup Python environment
      run: |
        python -m venv .venv
        source .venv/bin/activate
        pip install -r python/requirements.txt
    
    - name: Run R tests
      run: Rscript R/analysis.R
    
    - name: Run Python tests
      run: |
        source .venv/bin/activate
        python python/app.py

CI Benefits

  • Automated Testing: Ensures code works in clean environments
  • Environment Validation: Confirms lockfiles are correct
  • Cross-platform Testing: Test on multiple R/Python versions
  • Deployment Triggers: Automatically deploy on successful tests

Presentation Tips for R Meetup

Structure Your Talk

  1. Start with Problems: Show real-world dependency conflicts
  2. Explain Concepts: Use simple analogies (apartments vs. houses)
  3. Live Demo: Initialize renv, snapshot, restore on “fresh” machine
  4. Show Cross-language: Demonstrate reticulate integration
  5. Deployment Demo: Deploy Shiny app to Posit Cloud
  6. Q&A: Prepare for common questions

Key Takeaways for Audience

  • Virtual environments are essential for reproducible data science
  • renv makes R environment management straightforward
  • Python’s venv + requirements.txt is the minimum viable approach
  • Lockfiles are your insurance policy for deployment
  • Start small: use renv on your next R project

Common Questions

  • “Isn’t this overkill for small projects?” No, the overhead is minimal and prevents future headaches
  • “What about conda?” Great for complex scientific stacks, but renv/venv are simpler for most R/Python work
  • “How do I handle system dependencies?” Virtual environments handle packages, but system libraries (like GDAL) need separate management

Conclusion

Virtual environments transform data science workflows from fragile, machine-dependent processes to robust, reproducible systems. By isolating dependencies and capturing exact versions in lockfiles, you ensure that your analyses will work consistently across different environments and over time. Whether you’re an R user dipping into Python or maintaining complex multi-language projects, mastering virtual environments will make you a more effective and confident data scientist.

The examples in this tutorial provide a solid foundation—start by applying renv to your next R project, and you’ll quickly see the benefits in practice.

```{text}
    - uses: actions/checkout@v4
    
    - name: Setup R
      uses: r-lib/actions/setup-r@v2
      with:
        r-version: ${{ matrix.r-version }}
    
    - name: Setup Python
      uses: actions/setup-python@v4
      with:
        python-version: ${{ matrix.python-version }}
    
    - name: Restore R environment
      run: |
        R -e 'install.packages("renv")'
        R -e 'renv::restore()'
    
    - name: Setup Python environment
      run: |
        python -m venv .venv
        source .venv/bin/activate
        pip install -r python/requirements.txt
    
    - name: Run R tests
      run: Rscript R/analysis.R
    
    - name: Run Python tests
      run: |
        source .venv/bin/activate
        python python/app.py
```

## CI Benefits

- **Automated Testing**: Ensures code works in clean environments
- **Environment Validation**: Confirms lockfiles are correct
- **Cross-platform Testing**: Test on multiple R/Python versions
- **Deployment Triggers**: Automatically deploy on successful tests

## Key Takeaways for Audience

- Virtual environments are essential for reproducible data science
- renv makes R environment management straightforward
- Python's venv + requirements.txt is the minimum viable approach
- Lockfiles are your insurance policy for deployment
- Start small: use renv on your next R project

## Common Questions

- **"Isn't this overkill for small projects?"** No, the overhead is minimal and prevents future headaches
- **"What about conda?"** Great for complex scientific stacks, but renv/venv are simpler for most R/Python work
- **"How do I handle system dependencies?"** Virtual environments handle packages, but system libraries (like GDAL) need separate management

Virtual environments transform data science workflows from fragile, machine-dependent processes to robust, reproducible systems.
